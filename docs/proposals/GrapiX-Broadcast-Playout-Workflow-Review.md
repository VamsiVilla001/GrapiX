# GrapiX Broadcast Playout Workflow Review

**Owner:** Codex  
**Review baseline:** `97d110c` (16 October 2026)  
**Method:** source inspection of the build plan, Playout shell/web UI, Playout service, MCP surface, control-plane contracts and conformance. No full operator workflow was run in Tauri for this review. Runtime behavior below is marked **unverified** unless stated otherwise.

This is a proposal document. It does not amend `GrapiX-Build-Plan.md` or either tracker. Status labels below describe the evidence available at this baseline; they do not change tracker states.

## Evidence boundary

The Playout Tauri surface is more than a clock: `Playout/web/index.html` includes manual Take ID/revision/hash entry, Cue/Take/Clear, Continue/Update/Out, engine Program metadata, output configuration and a sequenced activity list. `Playout/src/` itself contains only clock-display rules (`Playout/README.md`, Layout). The service has immutable published revisions, pinned hashes, intent calls and a persisted rundown cursor (`services/playout/src/lib.rs`). These service capabilities are not yet connected to an operator library, fill form, rundown UI, or picture monitors. The shipped Tauri workflow and the service-level helpers must be assessed separately.

Phase 12 states are mixed: `12.1` is active while `12.4`, `12.6` and `12.7` are done in `progress.json`. This is not automatically a dependency violation: those rows depend on Phase 6 service steps, and each has a narrower criterion than a complete signed Playout application. However, the plan currently gives no product-level gate requiring the shell and all operator paths to work together. Therefore “Phase 12 complete” cannot be inferred from those three rows; the done claims should be read only as their individual criteria, and rechecked against the `12.1` shell before release.

### Protocol observations

CasparCG AMCP demonstrates a useful vocabulary for channel/layer targeting and distinct load, play, update, next and clear commands; its published graphics API is stateful and can update template data while displayed. Ross XPN exposes an external graphics-control command path. GrapiX should adopt the operational affordances only where needed, while maintaining typed, authenticated, hash-pinned and engine-frame-committed requests. No protocol behavior here was exercised against a live vendor system.

**Dependency amendments to consider:** add authored phases (`11.25`, then stop-point behavior `11.53`) to `12.4`; make the proposed Playout operator-form row depend on `11.26` and `11.54`; make `12.5` depend on `5.4` actual media transport; and make any live-update extension to `12.4` depend on the data contract and propagation/failure rules (`19.2`, `19.6`, `19.8`). Keep static cue/take snapshots usable before live data is built.

**Draft Done when:** In the running Editor Tauri app, create a lower third with named In/Hold/Continue/Update/Out phases and typed required fields; publish it to an immutable revision/hash. In the running Playout Tauri app, find that revision in the library, add it to a persisted rundown page, fill the typed form, pass readiness, and show its frame in Preview with the pinned revision/hash. Cue, take to Program, update one field that is explicitly live-updatable, continue through a stop point, run Out and clear the targeted page. Record each engine-committed frame and compare Preview to Program under the declared pixel tolerance. Inject repeated requests and disconnect/restart before send, after send/before reply, and after reply; prove there is no unintended duplicate take or clear and that reconnect reconciles from engine status. Remove and restore a font/asset to prove named readiness/refusal. Run the full `npm run check` gate. A future approved row must name a real media transport and target hardware for any native-resolution monitor claim; hardware tests remain blocked on `15.1`.
