1. What a frame of an animated text cost before (the probe is docs/evidence/11.61/tools/probe_text_frame_cost.rs)
   320x180, one text layer, 20 frames, milliseconds a frame and GPU resource builds a frame:
                                        DX12                 Vulkan               builds
     static text                        2.0                  1.2                  0
     geometry-only animator, 15 glyphs  3.5                  2.8                  4
     geometry-only animator, 64 glyphs  5.0                  3.7                  4
     opacity animator, 15 glyphs        13.9                 12.4                 30
     opacity animator, 64 glyphs        48.8                 41.1                 112
   The CPU reference path took 7 to 9 ms a frame in every case.
   Why: text is shaped once at prepare and its glyph outlines are cached; a frame only places them. But a text whose glyphs each
   have their own paint (an opacity or fill animator) is one path a glyph, and every path was its own coverage texture, Vello
   render, draw record, bind group and GPU submission, every frame.

2. The decision, asked before any code (gpu-glyph-instances-input.json, jev-laya-gpu-glyph-instances.json)
   Jev (jev-1.14.0): draw the paths of a layer into one coverage atlas and composite from one draw record a path
   (confidence 0.60; the alternatives 0.26 and 0.01); hold it to the same bytes as the path-by-path drawing (confidence 0.85);
   for every multi-path source (0.53); pack into several atlases when one is too small (0.62). On whether that alone lets the
   clause be recorded as met: 0.37, leaning no.
   Laya (laya-multilingual, max_len 8192, not truncated): near-flat on every choice (margins of 0.02 to 0.05) and chose a new
   instanced triangle pipeline; "yes" at 0.96 on the clause. A second opinion, not a vote. Not built: that pipeline's edge coverage
   is not Vello's, so the GPU and the CPU reference would stop agreeing within one code value, against the user's 15 Nov decision
   that Vello gives the coverage.

3. What the first version showed (the GPU alone draws through an atlas)
   Fast: opacity animator, 64 glyphs, 48.8 -> 5.9 ms on DX12 and 41.1 -> 3.6 ms on Vulkan; 15 glyphs 13.9 -> 4.3 and 12.4 -> 2.6;
   builds 112 and 30 -> 4 a frame.
   NOT the same bytes as the path-by-path drawing, so Jev's preferred criterion could not be met: of 15,960 and 20,970 pixels,
   15 and 79 differed, the worst by 0.0030 of full scale (0.76 of one 8-bit coverage step); with a small atlas (offsets under 64
   pixels) 3 pixels, worst 0.0020. Cause: a path moved by whole pixels to its cell rounds differently in f32 (a coordinate near
   1,100 keeps 128 times less of its fraction than one near 10), which flips one coverage code in a few edge pixels.
   The same measurement showed that path by path the GPU is the CPU backend to 1.2e-7 (a float's last place). So an atlas on the
   GPU alone would have spent the GPU/CPU gate's whole margin. Put to the user as three options; the user chose the third:
   the atlas on, with the CPU reference packing its paths the same way.

4. What is built
   services/render-engine/worker/src/rasterise/mod.rs    PreparedPath::instance (false unless set)
   .../rasterise/lyon.rs                                 prepare_text marks the per-glyph paths of a text animator
   .../rasterise/vello.rs                                plan_coverage (one plan for both backends), cell_transform, SHEET_SIDE;
                                                         VelloCpuRasteriser draws from the plan
   .../compositor/draw.rs, draw.wgsl                     GpuDrawer draws from the same plan: one Vello render a sheet, one compose
                                                         dispatch a path from its draw record (cell, window, paint) at a dynamic
                                                         uniform offset
   .../render_work.rs, text.rs                           RenderWork::cpu_text_shapings, counted in shape_object
   Rules of the plan:
   - Only instance paths (the per-glyph paths of a text animator) share a sheet. Every other path (rects, shapes, strokes, static
     text, paint) is a sheet of its own, the size of its window, at (0, 0): the drawing as it was, on both backends. So no frame
     that existed before moves.
   - An instance path's cell is slot k of a grid: k is its place among the instance paths, counted whether or not it is visible or
     inside the region; the pitch is the next power of two above the largest of their windows before the region clamps it. So a
     glyph keeps its cell when a neighbour's paint changes or a neighbour leaves the frame, and the CPU reference drawing onto the
     canvas and the GPU drawing into a layer of its own give one glyph the same cell.
   - A path the region cuts keeps its slot and is drawn alone (the edge of its own sheet cuts it).
   - A shared sheet larger than the device's texture limit refuses by name; it is never packed differently from the CPU's.
   Still done every frame, and said so: Vello rasterises each visible glyph's coverage again, because a transform changes coverage.
   What a frame no longer does: shape text; build a texture, a buffer, a bind group and a submission for each glyph.
   The milliseconds in section 3 are of the first version (a shelf atlas on the GPU alone). The version that is built (grid cells,
   both backends) has not been timed again; what is asserted of it is the count: the GPU builds the same for 64 glyphs as for 15,
   at most 6 a frame (the colour_reference test in section 5, green on DX12 and on Vulkan).
