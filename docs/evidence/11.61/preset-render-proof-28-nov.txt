3. What the proof found
   Before the fix below, trackingIn failed at frame 0 on the CPU path, on DX12 and on Vulkan: 85 pixels in the box
   x 187..197, y 80..91 (the last "e" of "reference") were [255, 255, 255, 0] where the hidden caption gives [0, 0, 0, 0].
   Cause: TextRangeSelector::weight measured the two edge distances of a Square range as fractions of the text, and `1 - centre`
   rounds. With the default whole range the last unit came out at 1 - 2^-53 for 241 of the lengths 1 to 512 (5, 10, 11, 13, 15...;
   the caption has 15 glyphs), so a glyph at animator opacity 0 kept an alpha of 1e-16: nothing drawn, its colour left in the frame.
   EffectCraft's range_value (crates/text/src/selectors.rs) rounds the same way, so the port was faithful.
   Fix (Shared/contracts/src/text_animator.rs): the distances are measured in units (index + 0.5, start * count, end * count), which is
   exact for a whole range; the same function otherwise. Two new tests: every length 1 to 512 at smoothness 1, 0.5 and 0 gives
   exactly 1 for every unit; a soft edge still selects by cover ([1, 0.5, 0, 0] for 4 units and a range of 0 to 0.375, hard [1, 1, 0, 0]).
   The 241 failing lengths were counted with the old formula in a Python one-liner, not by running the old Rust against the new test.
   The Editor holds no copy of this maths.
   Not changed, noted: an alpha that small is written out as full colour at alpha 0 by the output encode. That is the compositor's
   behaviour (rows 3.15 / 3.21), outside this claim.
